## 一、确认技术依据和开发环境

1. 检查 `docs/source/` 是否有用户明确注明最终版的 3.2；有则核对整理版与最终版的差异，以最终版为依据。没有则依据 `docs/TECHNICAL_ROUTE.md` 开展当前阶段，把待核对项写清，不阻塞不冲突的工作。
2. 只检查与项目有关的操作系统、CPU、内存、GPU、驱动、磁盘挂载与余量，以及 Python、Git、Node、Conda 等工具是否可用。不要读取或输出无关账号配置、密钥和私人文件。
3. 将实际环境记录到 `docs/ENVIRONMENT.md`。选择兼容的依赖，在数据盘创建本项目独立环境；优先利用现有可用工具，不删除环境、不重装驱动、不全局升级软件。
4. 若尚未初始化 Git，在当前项目目录初始化本地仓库。保留现有文件，不添加远端、不推送。核对 `.gitignore` 和 `.env.example`。

## 二、建立可追踪的工程结构

1. 根据实施计划确定目录布局和初期技术栈，记录理由；保持三层核心方法清晰，不为本轮工作拆分大量服务。
2. 为世界状态、施工事件、约束、飞行任务、冲突证据、补证请求、维护候选、计划采纳定义结构化模型，写入 `docs/DATA_CONTRACTS.md`。统一 ID、单位、坐标和高度基准、时间区间语义、数据来源与版本字段。
3. 更新 `docs/FEATURE_MATRIX.md`，逐项保留全部技术路线。分别标记“未实现、接口已定义、已实现未验证、已验证、待训练、待接入”等实际状态，不用单一完成百分比掩盖差异。

## 三、完成本轮最小端到端功能

使用包内明确标注的合成示例，完成实际可运行的确定性流程：

**读取 JSON → 建立几何对象与语义关系 → 应用施工事件 → 生成时空约束 → 检查既有任务 → 生成维护候选 → 独立复核候选 → 输出结构化结果。**

具体要求：

- 参数化表达园区、建筑、吊装设备和活动范围；保存来源及变更前后版本。
- 实现正常结束、延期和结束状态未确认的情景差异；设备仍在场时保留相应物理占用。
- 实现保守候选筛选和显式时空冲突检查。明确本轮支持的几何类型；对不支持的数据返回状态，不静默判安全。
- 建立初期航路图，在当前范围内采用安全时间区间方法生成延后或绕行候选；先支持确定速度和有限资源约束。若首轮确有阻塞，交付已完成链路并明确具体阻塞，不能用固定字符串冒充规划器。
- 候选必须带约束、时间、版本、变更幅度和可行性条件；使用独立复核入口检查。先不自动更新现行任务。
- 提供一个命令行或后端接口入口及结构化输出，保证后续前端能够接入。本轮优先完成计算链路，界面不作为首轮验收前提。

## 四、保留学习能力的正确接入位置

为 VLM/LLM 信息解析、XGBoost 敏感性、GNN 多任务关联、校准、主动补证和学习排序定义可替换接口及输入输出约定。

本轮不批量下载权重、不训练大型模型。未接入服务或没有训练产物时明确返回 `not_configured`、`not_trained` 或相应状态；确定性规则回退要标注来源。不要报告模型准确率、校准覆盖率或真实环境安全效果。

主动补证只能查询已提供的记录或明确标注的合成证据源，查询不到就保留未知；不能自己生成一个方便规划通过的答案。
